# Calling a Separate Program

Scope: a program calling another CSECT that is link-edited into the same load module, as in SB01CALL calling SB02SUBR: the register contract (R1, R13, R14, R15), the parameter list with the high bit on the last address, a hand-built `BALR` call and the `CALL` macro, the `V`-type constant and the link-edit step, the called program's save area and exit, and the return code in R15. Entry and exit linkage of a main program is in the linkage article, and internal `BAL` routines are in the subroutines article. `LINK` appears only in a comment of SB01CALL and was not run, so it is compared with `CALL` and not described further. Programs loaded by name at run time, re-entrant programs and the `PARM` field of the job step are not used in any program and are not described. The programs were not assembled or run, apart from the run shown in the SB01CALL SYSOUT screen.

Source programs: SB01CALL (caller), SB02SUBR (called).

## Central Idea

An internal routine shares the caller's registers and storage. A separate program does not: it has its own base register and save area, receives the addresses of its data in a parameter list, and returns a number in R15. Four registers carry the agreement between the two programs.

## The Register Contract

| Register | At the call | At the return |
|---|---|---|
| R1 | Address of the parameter list | Not defined |
| R13 | Address of the caller's save area | The same value, restored by the called program |
| R14 | Return address | Restored by the called program |
| R15 | Entry address of the called program | Return code |

The caller loads R1 and R15, then `BALR 14,15` sets R14 and branches. The called program saves the caller's registers into the caller's save area (`STM 14,12,12(13)`) before it changes any of them.

## Three Ways to Make the Call

```
         MVC   AMOUNT,=F'50'
         LA    1,PARMLST1              * R1 = parameter list
         L     15,=V(SB02SUBR)         * R15 = entry address
         BALR  14,15                   * R14 = return address, branch
         BAL   10,SHOWRC
         ...
         CALL  SB02SUBR,(TOTAL,AMOUNT) * The same call by macro
         ...
*        LINK  EP=SB02SUBR,PARAM=(TOTAL,AMOUNT)   (comment only)
```

| Form | How the target is found | Used in SB01CALL |
|---|---|---|
| `LA` / `L` / `BALR` | `V`-type constant resolved by the linkage editor | Call 1 |
| `CALL` macro | The same, generated by the macro | Calls 2 and 3 |
| `LINK` macro | z/OS locates and loads the program by name at run time | A comment only |

- All three leave R1, R13, R14 and R15 as in the table. The called program cannot tell which was used.
- Per the SB01CALL source comments, `CALL` is resolved at link-edit time with no library search, and `LINK` is a supervisor call that loads a separate program by name.
- Only the `LA` and `L` lines are written out by hand. `PRINT NOGEN` hides the macro expansion in the listing.

## The Parameter List

```
PARMLST1 DC    A(TOTAL)                * Word 1: address of parameter 1
         DC    X'80',AL3(AMOUNT)       * Word 2: last address, bit 0 on
```

- The list is one fullword per parameter, each the address of the data. The called program reads the data through those addresses, so it can change the caller's field.
- `AL3` is a 3-byte address. With the 1-byte `X'80'` it fills one fullword with bit 0 on. Bit 0 on the last word tells the called program where the list ends.
- SB02SUBR reads both words and clears the flag from the second: `L 3,4(,1)` then `N 3,=X'7FFFFFFF'`. It never tests the flag and does not check how many parameters were passed.
- The source comments say the `CALL` macro sets the flag automatically. Per SB01CALL.md it sets the flag only when `VL` is coded, and `VL` is not coded. The result is the same, because SB02SUBR does not test the flag.

## Finding the Called Program

- `=V(SB02SUBR)` is an external reference. The assembler leaves the address blank and the linkage editor fills it in.
- SB02SUBR is assembled in its own step to its own object deck. The link-edit step reads both decks from `SYSLIN`, `&&OBJ1` then `&&OBJ2`, and produces one load module. If SB02SUBR is missing from `SYSLIN`, the link-edit step reports the reference as unresolved.
- With the entry point of the load module at SB01CALL, SB01CALL is the program that runs and SB02SUBR is code inside the same module.

## Inside the Called Program

```
SB02SUBR CSECT
         STM   14,12,12(13)            * Caller's registers into caller's area
         LR    12,15                   * R12 = my base
         USING SB02SUBR,12
         ST    13,SUBSAVE+4            * Backward chain
         LA    14,SUBSAVE
         ST    14,8(,13)               * Forward chain
         LR    13,14                   * R13 = my save area
         L     2,0(,1)                 * R2 = address of total
         L     3,4(,1)
         N     3,=X'7FFFFFFF'          * R3 = address of amount
         L     4,0(,2)
         A     4,0(,3)
         ST    4,0(,2)                 * Total back to the caller
         LTR   4,4
         BM    SUBRBAD                 * Negative: return code 4
         MVI   RETCODE,0
         B     SUBRRET
SUBRBAD  MVI   RETCODE,4
SUBRRET  L     13,SUBSAVE+4
         LM    14,12,12(13)
         IC    15,RETCODE
         BR    14
```

- The save area `SUBSAVE` belongs to SB02SUBR. It is chained both ways: word 2 holds the caller's area, and word 3 of the caller's area holds `SUBSAVE`.
- R13 is changed to `SUBSAVE` for the rest of the routine and restored from `SUBSAVE+4` before the `LM`.
- The return code is kept in the one-byte field `RETCODE`, because `LM 14,12,12(13)` reloads R15 and would erase a code placed there earlier.
- `SUBSAVE` and `RETCODE` are static storage in the CSECT. A second call while the first is active would overwrite them, so SB02SUBR is not re-entrant.

## The Return Code

The caller reads R15 straight after the call. `SHOWRC` starts with `ST 15,SAVERC` because the `PUT` that follows uses R15.

| Call | Form | AMOUNT | TOTAL after | Return code set by SB02SUBR | RETURN CODE printed |
|---|---|---|---|---|---|
| 1 | `BALR` | 50 | 150 | 0 | 33280 |
| 2 | `CALL` | 500 | 650 | 0 | 33280 |
| 3 | `CALL` | -100000 | -99350 | 4 | 33280 |

The totals are correct. The return code is not: X'00008200' appears on all three lines, including the third, which should show 4.

Reading in SB01CALL.md and SB02SUBR.md, inferred from the source and the SYSOUT:

- `LM 14,12,12(13)` restores R12 to SB01CALL's base register.
- `IC 15,RETCODE` is addressed through R12. After the `LM` the assembled displacement of `RETCODE` is added to SB01CALL's base, so the byte read is not `RETCODE`.
- `IC` replaces only the low byte of R15. The upper three bytes are what `LM` restored, the entry address of SB02SUBR.

The source is not changed. The fix suggested in the docs is untested: set R15 with `SR 15,15` and `IC 15,RETCODE` before the `LM`, while R12 is still valid, then `L 13,SUBSAVE+4`, `ST 15,16(,13)` and `LM 14,12,12(13)`. `ST 15,16(,13)` stores the code into the caller's save area, in the position `LM` reloads into R15.

## What Went Wrong First

The first run of SB01CALL abended S0C4 right after the heading line.

- The hand-built call had `L 15,=V(SB02SUBR)` and `BALR 14,15` but no `LA 1,PARMLST1`.
- R1 held what `OPEN` and `PUT` had left in it.
- SB02SUBR's first use of the list, `L 2,0(,1)`, used that value as an address.
- The abend hid the return-code defect. It appeared only after the call worked.

## Rules

- Load R1 before every call that passes a list, and load R15 with the entry address.
- Keep the last parameter's high bit on, and clear it before using the address.
- Save the caller's registers first in the called program, and restore them last.
- Give the called program its own save area and chain it both ways.
- Set the return code after the `LM`, using a register or storage that is still valid.
- Clear the other three bytes of R15 before `IC`.
- Save R15 in the caller before any macro runs.
- Include every object deck in `SYSLIN` of the link-edit step.
- Check the return code of each call, and test the case that gives a nonzero code.

## Common Failures

| Symptom | Cause | Fix |
|---|---|---|
| S0C4 at the first use of the list | R1 not loaded | `LA 1,list` before the call |
| Unresolved external reference in the link-edit | SB02SUBR deck not in `SYSLIN` | Add `&&OBJ2` |
| Address of the second parameter is garbage | High bit not cleared | `N reg,=X'7FFFFFFF'` |
| Return code differs from the one set | `LM` reloaded R15, or the base register changed | Set R15 after `LM` through a valid base, clear its other bytes |
| Return code lost in the caller | R15 reused by `PUT` | `ST 15,SAVERC` first |
| Caller's registers wrong after the call | Called program did not restore them | `STM` first, `LM` last |
| Wrong results on a second, nested call | Static save area reused | Do not call it again while it is active |
